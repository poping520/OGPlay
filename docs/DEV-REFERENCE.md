# OGPlay 开发设计参考

> 按需参考：仅在用户明确要求读取或使用本参考时查看。日常开发不主动加载，
> 不作为默认开发指令，也不替代项目现行契约、ADR 或具体任务要求。

本节逐项积累适用于 OGPlay 的开发方法；每项都有适用条件，不要求所有模块采用同一实现路线。

## 方法一：framework 按需裁剪，最小实现保持通用

**以游戏持续可玩为目标，由真实需求驱动 framework 的实现范围；优先简化内部机制，
保留范围内必要的 Android 可观察行为，以最小充分的通用能力降低长期开发与维护成本。**

OGPlay 不追求完整 AOSP。游戏启动时触达 framework API，不等于持续运行依赖其全部功能；
不能因一个缺失类型或方法，就默认补齐整个类族或子系统。进入 native/GLES 是阶段目标，
仍需识别后续经 JNI 使用的资源、输入、音频、存档、线程和生命周期等必要能力。

本方法用于决定“实现多少”；方法二用于决定“选什么底座兑现已确定的契约”。
两者均不授权绕过现行模块契约；调整既有架构或支持边界时，按项目约定记录决定。

### 按实际作用选择最小范围

| 实际需求 | 默认策略 |
| --- | --- |
| 加载、继承、接口与签名解析 | 提供准确类型结构与必要依赖；不因此承诺对应行为已实现 |
| 配置、监听登记、进程内状态查询 | 用轻量状态实现必要的设置、读取、默认值与隔离 |
| 可选设备或外部服务 | API 契约允许时，统一发布真实的无设备、无服务或无数据状态 |
| 非核心展示与装饰效果 | 评估降低表现保真度，但不得任意改变必要状态、回调或控制流程 |
| 游戏持续运行的关键路径 | 实现实际依赖的行为，不能以“只需过启动”为由省略 |

调用次数少、只在启动时调用、属于广告或辅助组件，均不足以证明其行为可省略。
返回值、异常、对象身份、状态变化或回调被后续逻辑消费时，应纳入必要契约。

### 通用性约束

- **游戏发现需求，通用能力定义实现。** 不依赖游戏名、包名、调用栈、特定输入常量或
  当前样本的调用顺序；不能将某个游戏不使用的分支直接认定为无意义。
- **裁剪功能范围，不裁剪成样例。** 范围内覆盖一般合法输入、重复调用和对象隔离；
  范围外保留可扩展边界，不为尚无需求的能力提前建设完整系统。
- **简化机制，保持行为一致。** 可以用进程内对象替代非必需系统服务，采用简单数据结构；
  相关查询、操作、状态与资源生命周期必须一致，复用唯一 VFS、Clock、线程及 UI 底座。
- **合法缺席优先于伪实现。** Android 契约允许的不可用结果可以是正式实现，并非一律抛异常。
  无操作仅在契约及环境允许时成立；禁止操作未完成却报告成功、无条件返回零或伪造完成回调。
- **近似需有边界与证据。** 降低非核心表现保真度时，明确记录差异、通用适用条件及验证结果，
  不宣称与 AOSP 等价。不能仅因当前游戏不在意，就改变时序、线程归属或控制流程。

### 实现路线与扩展条件

BootDex、intrinsics 和自有 facade 都是手段，以兑现必要契约的长期总成本选择路线。
原版 Java 自洽且依赖可控时优先纳入 BootDex；依赖庞大系统服务而需求有限时，评估通用
轻量 facade，也可组合原版类型、Java 逻辑与平台边界。不能为遵循某一路线机械补齐整个生态，
也不能为短期少写代码而重复建立算法、状态或资源所有权。

遇到缺口时，依次确认：

1. **实际依赖。** 区分只需类型可链接、实际调用，以及返回值或回调影响后续流程。
2. **最小契约。** 判断合法不可用路径是否足够，明确通用支持范围、必要行为及排除项。
3. **实现成本。** 比较原版依赖闭包与轻量实现的维护成本，选择可自然扩展的实现。
4. **定向验证。** 除触发样本外，覆盖相关的不同参数、重复调用、对象隔离及取消/释放等场景；
   仅对范围内相关行为设置检查，不自动扩展为完整 API 矩阵或 CTS 验收。
5. **按证据扩展。** 新的真实依赖出现后提高完整度。分别记录类型可链接、有限行为支持与
   真实游戏运行结果，不能将越过首错或进入 native 当成完整能力或游戏可玩。

通用性不等于一次实现更多 API，而是让已实现的小范围具有稳定语义，其他游戏可复用，
后续需求可扩展。它不能保证所有游戏兼容，但应避免为推进一个游戏而制造其他游戏的障碍。

## 方法二：契约驱动兼容，底座最小充分

**以应用可观察行为为兼容契约，优先复用原版与成熟实现；对不必复刻的系统内部机制，
采用 OGPlay 自有的最小充分底座，并通过测试证明兼容性。**

OGPlay 面向游戏进程的通用能力，不以复刻 Android 系统为目标。公开 API/ABI 与约定行为
对齐目标 AOSP 版本，内部服务、进程和存储结构按实际需要实现。“最小充分”指完整兑现
已声明范围所需的最小实现；优化目标是长期总成本，而非代码最少、依赖最少或最快越过报错。

### 适用条件

- 能明确划分应用契约与内部机制，内部可经稳定接口替换。
- 直接搬入 AOSP 底座会引入超出项目范围的系统服务，或显著增加维护成本。
- 现有 OGPlay 基础设施或成熟库可实现所需行为，并能通过独立测试证明。

### 实现路线的选择

无论是否满足自有底座的条件，都先评估原版与成熟实现；三种路线可以组合使用。

| 路线 | 优先采用的情况 | 必须评估的代价 |
| --- | --- | --- |
| 复用原版 AOSP | 普通 Java 状态、格式和算法语义可独立运行，依赖可控 | 依赖闭包、ABI、版本限制和补丁维护 |
| 复用成熟后端 | 密码、TLS、图形等复杂机制已有可靠实现 | 许可证、平台支持、安全更新和适配成本 |
| 自有最小充分底座 | 原版依赖庞大系统服务，但所需契约可用进程内服务兑现 | 语义维护、测试覆盖、并发隔离和后续扩展成本 |

只有在契约可兑现、总成本更低且边界可验证时，才选择自有实现。不能仅因“属于底层”
就重写，也不能用减少库数量替代技术判断。既有 Bionic、BootDex、ANGLE 等选择继续遵循
各自契约；涉及架构变化时先记录 ADR。版本与安全策略偏离目标 AOSP 时，应显式记录差异，
不能一边改变行为，一边宣称完全一致。

### 不可简化与可替换的边界

| 必须按约定兑现的应用契约 | 可按需替换的内部机制 |
| --- | --- |
| 类/方法/ABI、类型关系、Provider 和服务查找 | 私有类结构、SPI 和内部适配方式 |
| 返回值、异常、状态转换、真实回调 | 进程内服务替代非必需 daemon/IPC |
| 生命周期、线程、资源释放、持久化与隔离 | 存储布局、索引、缓存和资源组织 |
| 格式互操作、权限与信任、密钥导出规则 | 满足相同约束的既有库或自有底座 |

“内部黑盒”须有证据：即使不是公开 SDK，应用仍可能通过反射、JNI、显式 Provider、
文件或 native 符号观察它。已被依赖的行为应纳入支持契约，或明确记为不支持，不能静默改变。

范围一旦声明，成功与失败语义都必须兑现：异常、回调、并发、持久化、隔离和资源释放
不是可选完善项。范围外明确失败并记账；明确失败只是边界诚实，不代表该能力已经兼容。
架构应允许同类应用复用和能力自然扩展，不为当前游戏的输入特制实现。

### 实施步骤

1. **从症状识别通用缺口。** 游戏调用作为触发证据，任务范围按通用能力定义，不做专用补丁。
2. **列出兼容契约。** 对照目标 AOSP 版本，明确支持范围、可观察行为、失败语义和排除项。
3. **选择最小充分底座。** 记录选择依据，比较依赖、适配、测试、安全更新及长期维护成本；复用唯一
   VFS、Clock、网络、线程和资源生命周期，不建立平行状态或绕行入口。
4. **按完整能力组织少量单元。** 将紧密依赖的 API、底层接入、测试和文档合并交付；
   只在存在独立验收出口或真实依赖边界时拆分，不为减少单元数省略验收。
5. **验证契约并如实发布。** 同时测试成功、失败、回调、并发、隔离、持久化及清理；
   按需要加入原版对照、格式互操作和真实集成证据。同步模块契约与能力账本，
   不把类可链接、单条路径通过或单游戏不再报错当作完整能力。

### 示例：证书信任与 TLS

保留 AOSP SSL/KeyStore 公开 API，自有 Java Provider 连接 guest libssl/libcrypto 和唯一
NetworkRuntime；AndroidCAStore 使用版本化 CA 包和只读视图，无需复制 Android 系统服务。
AndroidKeyStore 若确有需求，可另做应用隔离的软件密钥底座，不必作为 TLS 前置依赖。

但 AndroidCAStore/AndroidKeyStore 类型本身可被应用访问：查询、异常、隔离与密钥导出等
语义仍必须兑现。不能用返回成功、跳过验证或伪造硬件保护代替实现。具体方案见
[信任验证与 TLS](design/dexvm/14-tls-trust.md)及 [ADR-0066](adr/dexvm.md#adr-0066)。
