# 09 · GC-B：精确非移动 STW 标记清除

本章把 [04 §5](04-integration.md) 的"B 期"展开为可实施的工程方案，写给
**实施阶段的 AI**：先盘点代码现状（§2 的事实锚点在动手前必须逐项核实），
再给出机制设计（§3–§9）、AOSP 参考对照（§10）、验证体系（§11）与 WU
分批（§12）。本章按 DVM-27..29 落地后的真实执行模型修订了 04 §5 的
停世界机制（见 §3 裁决记录）；与 04 §5 冲突处以本章为准。

实施纪律沿用 [06 §3](06-migration.md)：上下文装载顺序为 `AGENTS.md` →
`docs/state/CURRENT.md` → 本章 → 当前 WU 涉及的 `MODULE.md`；实现任何
GC 语义前必须研读 §10 指定的 AOSP 文件并在测试注释记录出处。

## 1. 目标与非目标

| 目标 | 判定 |
| --- | --- |
| 回收不可达 VM 对象，长时游玩堆水位有界 | 长运行 Scenario 中 `allocated_bytes` 在 GC 后下降且不单调增长 |
| OutOfMemoryError 只在"真垃圾已全部回收仍不足"时抛出 | OOM 前强制一次全量回收（对照 AOSP `GC_BEFORE_OOM`） |
| 对既有 exact gate 透明 | A5/A6/DH 现有 Scenario 三轮逐位持平 |
| 宿主资源随对象死亡释放 | 宿主背衬实例清扫时调用声明的宿主状态析构 handler |
| 全程确定性 | 无 wall clock 参与；GC 时点由分配流决定，暂停以 tick 计 |

**非目标**（01 §3 既有非目标继续有效）：

- 并发/增量标记、分代、压缩/移动——对象非移动、句柄稳定是对象模型
  硬性质（02 §6），永不推翻；
- `finalize()` 执行、`ReferenceQueue`、软引用时效语义——弱/软/虚引用
  一律按强引用处理并记账（04 §5 既定）；JNI weak global 的既有清除
  语义（`ClearWeakReferencesTo`）是唯一弱语义，由 GC 兑现；
- 堆内存真实归还宿主 OS（`madvise` 类优化）——预算 arena 的容量记账
  下降即为"回收"，宿主内存复用交给 C++ 分配器。

**AOSP 参考红线**（07 §3 细化）：`vm/alloc/CardTable.cpp`、
`WriteBarrier.h`、`Copying.cpp`、`HeapSource.cpp` 的 dlmalloc 双堆与
footprint 管理是并发/分代/移动专用，**不参考**。只参考
`MarkSweep.cpp`/`Heap.cpp`/`Visit.cpp` 的根口径、标记遍历与清扫时序。

## 2. 现状盘点（实施前事实锚点）

GC-A 已交付（DVM-8）：`JavaObjectModel::Impl::Reserve` 只做字节记账
门闩，耗尽抛 `heap_budget_exhausted`，解释器经 `SetEmergencyReserve`
物化真实 OOM。下表是 GC-B 触及的全部存量事实，实施前逐项核实：

| # | 事实 | 位置 | GC-B 动作 |
| --- | --- | --- | --- |
| 1 | `records`/`instance_storage`/`object_arrays` 只增 vector，句柄=records 下标+1 | `src/runtime/dexvm/object_model.cpp` | 三者加空闲链复用；记账双向 |
| 2 | 帧寄存器带精确 tag（`SlotTag::ref`） | `interpreter_internal.h` `Frame::regs` | 精确根扫描的既有兑现，直接用 |
| 3 | 执行 context 表：`Impl::executions` + `default_execution`，帧栈、`pending_exception`、`exit_result`、`Frame::last_result/caught` 均可含 ref | `interpreter_internal.h` | 全部 context 全部帧入根集 |
| 4 | 静态字段槽是裸 u32（`LinkedClass::static_storage`），无 tag，但 `own_static_fields` 的 descriptor 可判 ref 性 | `include/ogplay/runtime/dexvm/class_linker.h` | 链接期预计算每类"静态 ref 槽下标表"（对照 AOSP `scanStaticFields` 按 `signature[0]` 判定） |
| 5 | **四张 intrinsic 侧表按句柄键控且持有 `VmObjectRef`**：`throwables`（message/cause）、`builders`（无 ref）、`lists`、`maps` | `interpreter_internal.h` `Interpreter::Impl` | "侧表即字段"契约（§5、§8）：随 owner 标记而 trace，随 owner 死亡而清 |
| 6 | `JniReferenceTable` 有 local/global/weak-global 三态与 `ClearWeakReferencesTo`，**无枚举 API** | `include/ogplay/runtime/jni/jni.h` | 新增 `VisitRoots`（枚举 local+global；weak 不是根） |
| 7 | 字符串/基元数组委托 session 级 store，二者均有 `Delete` | `jni_object.h` / `jni_array.h` | 清扫时对 store 背衬记录调用 `Delete` |
| 8 | `VmExecutionLock` 串行化全部解释执行与 intrinsic；阻塞原语经 `ReleaseForBlocking` 停泊 | `interpreter_context.cpp` | 执行锁即停世界（§3） |
| 9 | 宿主背衬实例只有 `host_state` u64，无析构 handler 声明口 | `intrinsic_builder.h` | builder 新增 `HostStateDestructor` |
| 10 | `Object.hashCode` 返回句柄值 | `intrinsics/java_lang.cpp` | 句柄复用改变后续 identity hash（§6 裁决） |
| 11 | `intern_table`、`class_objects` 是 object model 内哈希表 | `object_model.cpp` | intern 表与 class 对象按强根处理（不朽） |
| 12 | `VmMonitorTable` 按对象身份键控 | `vm_monitors.h` | 清扫时清除死对象的 monitor 记录（wait-set 成员必然被停泊线程帧根住，见 §4） |
| 13 | `by_identity` 身份→记录映射（`BindString` 会改绑） | `object_model.cpp` | 清扫时按记录当前 identity 擦除 |
| 14 | `VmThreadRuntime` 持各线程的 Thread 对象与 context | `vm_threads.h` | Thread 对象入根集 |
| 15 | `<clinit>` 状态在 `LinkedClass::clinit_state` | `class_linker.h` | 类对象不朽（见 11），无需单列 |

## 3. 执行模型与停世界

**裁决（修订 04 §5）**：04 §5 设计了"全局 safepoint 标志 + 方法入口/
回边/分配点轮询"的握手。该设计写于阶段 4 线程模型落地前；DVM-27..29
之后，**同一时刻只有一个宿主线程解释字节码**（`VmExecutionLock`，
`src/runtime/dexvm/MODULE.md` 不变量）。因此**执行锁本身就是停世界**：
GC 在持锁的分配点运行时，其余线程只可能处于三种状态，帧全部稳定——

| 其余线程状态 | 帧为何稳定 |
| --- | --- |
| 阻塞在 `Call`/`EnsureClassInitialized` 入口或 `ReacquireAfterBlocking` 等锁 | 帧只在持锁时变异 |
| `Object.wait`/monitor 竞争/`join`/`sleep` 停泊（safe region） | 停泊前经 `ReleaseForBlocking` 整体让锁，帧冻结 |
| 执行 guest native 代码 | native 侧引用必经 JNI 引用表（根集），guest 内存不藏 VM 句柄；且 native 出向调用期间调用方持锁，GC 根本不会并行 |

不新增任何轮询、原子标志或握手协议。safepoint 轮询设计**废弃**。

**安全分配点（封闭集）**：回收只允许在解释器主循环 `Step` 内、下列
分配指令 handler 的最前端触发——此刻该指令尚未产生任何未根化句柄，
全部活跃引用都在 tagged 寄存器/根集内：

```text
new-instance (0x22)   new-array (0x23)
filled-new-array (0x24)   filled-new-array/range (0x25)
const-string (0x1a)   const-string/jumbo (0x1b)
```

**intrinsic、JNI 入向与异常路径的分配不触发回收**。这些路径在 C++
栈上持有未根化的新鲜句柄（如 `ThrowJava` 在 `SetPending` 之前、
集合 intrinsic 在 `iterator()` 填槽之间），回收会把刚分配的对象当
垃圾清掉。AOSP 用 `dvmAddTrackedAlloc` 临时根表解决同一问题
（`Heap.cpp` `dvmMalloc` 的 `ALLOC_DONT_TRACK` 注释）；我们用
"安全点限定"替代——不引入临时根表，代价是水位阈值与硬预算之间
必须留出余量（§7）：两个安全分配点之间的 intrinsic 分配靠余量吸收，
余量内仍耗尽预算即走既有真实 OOM 路径（诚实，不凑合）。

**配套不变量**（进 `MODULE.md`）：阻塞原语不得跨 `ReleaseForBlocking`
在 C++ 栈上持有未根化的新鲜句柄。现有 wait/sleep/join/monitor 路径
均满足（不分配）；新增阻塞 intrinsic 时逐个复核。

## 4. 根集

对照 AOSP `MarkSweep.cpp` `dvmHeapMarkRootSet` 的注释清单逐项映射。
根访问统一走一个 `RootVisitor`（回调收 `VmObjectRef`），每个根类别
一个枚举函数，可单独测试：

| 根类别 | 我方位置 | 所需新 API |
| --- | --- | --- |
| 全部执行 context 全部帧的 `SlotTag::ref` 寄存器 | `Impl::executions` + `default_execution` → `frames[*].regs` | context 表遍历（持 `executions_mutex`，本就在执行锁内） |
| 帧的 `last_result`、`caught`；context 的 `pending_exception`、`exit_result` | 同上 | 同上 |
| 类静态 ref 槽 | `LinkedClass::static_storage` | 链接期预计算 per-class 静态 ref 槽下标（事实锚点 4） |
| JNI local + global 引用表（native 持有的一切必经此处） | `JniReferenceTable` | `VisitRoots(visitor)`：枚举全部线程 local 帧与 global 表；weak global **不是**根 |
| intern 表 | `JavaObjectModel::Impl::intern_table` | model 内部直接标 |
| class 对象表 | `JavaObjectModel::Impl::class_objects` | 同上（类对象不朽：数量有界=已链接类数，永不回收） |
| Thread 对象 | `VmThreadRuntime` 线程记录 | `VisitThreadRoots(visitor)` |
| throwable 侧表的 message/cause | `Impl::throwables` | **不是根**——随 owner throwable 被标记时 trace（§5）；owner 不可达则整条陪葬 |
| 紧急保留期物化中的 OOM throwable | `pending_exception` 已覆盖 | 无 |

wait-set 与 monitor 竞争队列**不需要**单列为根：成员线程停泊时其帧
仍在 context 表内（receiver 在帧寄存器里），已被第一行覆盖。JNI
`PublishGlobalObjectForHle` 发布的宿主长期持有对象在 global 表内，
已被第四行覆盖——宿主代码裸存 `JniObjectIdentity` 不经引用表属于
既有契约违规，GC 使其从"泄漏"变为"悬垂"，列入风险表（§13）。

## 5. 标记

非移动精确标记，对照 `MarkSweep.cpp` 的 `markObjectNonNull` /
`processMarkStack` / `scanObject`（immune region、finger、并发重标记
不参考）：

- **mark 位**：`std::vector<bool>`（或位图）按 records 下标索引，每轮
  GC 重建——不常驻对象头，对象布局零改动。
- **灰栈**：`std::vector<VmObjectRef>`；根访问器把未标记对象置位并压栈，
  然后循环弹出扫描，直到空。
- **逐 kind 扫描规则**（对照 `scanObject` 按类型分派）：

| VmObjectKind | 扫描内容 |
| --- | --- |
| `vm_instance` | `InstanceSlots` 中 `SlotTag::ref` 槽（tag 即精确性，无需类布局二次推导）；owner 的 class 对象若已物化则标记 |
| `object_array` | 全部元素 |
| `host_backed` | 仅其 class 对象 + **侧表 trace hook**（下） |
| `string` / `primitive_array` | 无出边（叶子） |
| `class_object` | 根集常驻，不进灰栈也不会漏（不朽） |
| `external` | 无出边（叶子） |

- **侧表 trace hook（"侧表即字段"契约）**：事实锚点 5 的四张表在
  逻辑上是 host_backed/throwable 对象的实例字段，只是物理上存在
  解释器侧。标记扫描到 owner 时按句柄查表并 trace：`lists[h]` 与
  `maps[h]` 的全部元素、`throwables[h]` 的 message 与 cause；
  `builders` 无 ref 不 trace。该契约在 §8 收口为封闭枚举 + 注册制。

## 6. 清扫

对照 `MarkSweep.cpp` `dvmHeapSweepUnmarkedObjects`（bitmap 差集 +
`madvise` 不参考；我们直接线性扫 records）。对每个未标记且非空闲的
记录，按顺序执行：

1. **宿主状态析构**：`host_backed` 记录查其类声明的
   `HostStateDestructor`（`IntrinsicClassBuilder` 新 API，声明即绑定
   通道，与 `Declare_*()` 同址）并调用，释放 voice/surface/文件句柄等
   宿主资源。这是对象模型的资源管理义务，**不是** finalizer——不执行
   任何 guest 字节码，handler 是宿主 C++。未声明析构的类默认无操作。
2. **委托存储释放**：`string`/`primitive_array` 记录调用对应 store 的
   `Delete(identity)`；`vm_instance`/`object_array` 归还
   `instance_storage`/`object_arrays` 槽位入各自空闲链；`external`
   记录只删身份映射（存储归 JNI 侧所有）。
3. **表清理**：`by_identity.erase(record.identity)`（`BindString` 改绑
   后以记录当前 identity 为准）；四张侧表 `erase(handle)`；
   `VmMonitorTable` 清除该对象的 monitor 记录（断言其无 owner、
   wait-set 为空——有则是根集缺陷，硬失败）；
   `JniReferenceTable::ClearWeakReferencesTo(identity)`（JNI weak
   语义在此兑现：weak global 解析开始返回 null）。
4. **记录回收**：记录置为空闲态并入 records 空闲链，`allocated_bytes`
   按该对象当初 `Reserve` 的口径回减（记录里补一个 `reserved_bytes`
   字段，分配时写入，避免清扫期重算）。

`intern_table` 与 `class_objects` 是强根，其成员永远被标记，清扫
不触碰——interned 字符串与类对象不朽是本设计的既定取舍（dex 字符串
字面量本就与镜像同生命周期；类数量有界）。

**空闲态记录的访问防御**：`At()` 对空闲记录明确失败（携带
`object_model_failure` + 句柄值），把"悬垂句柄"从静默别名变成可
诊断错误——在句柄被复用前的窗口内有效，属尽力而为的调试面而非
安全承诺。

**句柄复用裁决**：空闲句柄进空闲链并被后续分配复用。后果是
`Object.hashCode`（= 句柄值，事实锚点 10）在跨 GC 的分配序列上会
出现重复值。裁决为**接受**：真机 Dalvik 的 identity hash 就是对象
地址，地址同样随 GC/malloc 复用而重复，游戏无法依赖其唯一性；我方
行为与设备同构。确定性不受影响——固定输入下分配流与 GC 时点确定，
句柄序列逐轮一致，exact gate 三轮比对仍然成立。不引入代际句柄
（generation bits）：它改变句柄空间语义、触碰全部现有测试，收益只是
把上述调试面从"窗口内"扩到"永久"，不值当。

## 7. 触发策略、预算与确定性

参数进 profile v2 `[runtime.dexvm]`（schema 校验器同步，受检范围
显式声明）：

```toml
[runtime.dexvm]
heap_budget_bytes = 536870912   # 硬预算（存量字段，语义不变：耗尽=OOM 路径）
gc_watermark_percent = 75       # 新增：分配点水位阈值，0 = 禁用 GC-B（quirk 面）
```

- **水位触发**：安全分配点处 `allocated_bytes + request >
  budget × watermark%` 即先回收再分配（对照 `Heap.cpp` `tryMalloc`
  的"先 GC 后扩堆"次序；我们无扩堆，只有回收）。
- **OOM 前最后一搏**：安全分配点处回收后仍超硬预算 → 抛真实 OOM
  （对照 `GC_BEFORE_OOM`；软引用清除项不适用，我们无软引用时效）。
  intrinsic 路径内耗尽硬预算 → 直接走既有 OOM 路径（§3 论证的余量
  护栏；`budget − watermark` 的差值就是 intrinsic 分配的安全空间，
  默认 25% = 128 MiB 量级，远大于单次安全点间隔的 intrinsic 分配）。
- **`System.gc()`**：维持只记账不强制（04 §5 既定），
  `intrinsics/java_lang.cpp` 的 System 段注释同步指向本章。
- **确定性**：触发条件只依赖分配流（字节数），不依赖任何时间源；
  GC 暂停时长以 tick 与结构化日志记录，不参与任何决策。固定步长
  模式下逐轮完全可重放。
- **关闭即失败**：`gc_watermark_percent = 0` 时行为必须精确回到
  GC-A（只分配不回收，耗尽 OOM）；依赖 GC 的测试在该配置下必须
  失败——这是 AGENTS 的 quirk 纪律在 GC 上的兑现。

## 8. 侧表契约收口

04 §5 的硬约束"宿主状态内不藏 VM 引用"在现状代码中已被四张侧表
事实上突破（事实锚点 5）。GC-B 不回退这四张表，而是把约束改写为
可执行的封闭契约：

1. **封闭枚举**：解释器允许持有 `VmObjectRef` 的 intrinsic 侧存储
   仅限注册过 trace + sweep hook 的表。现状四张：`throwables`
   （trace: message/cause；sweep: erase）、`builders`（trace: 无；
   sweep: erase）、`lists`（trace: 全元素；sweep: erase）、`maps`
   （trace: 全键值；sweep: erase）。
2. **注册制**：新增侧表必须同 WU 内注册两个 hook，缺一即装配期
   失败（不是运行期漏标）。
3. **`host_state` 禁令不变**：u64 `host_state` 永远不解释为
   `VmObjectRef`；需要 owner→VM 对象的边一律走注册侧表或实例槽。
4. **机器判定**：测试枚举注册表并与 `Interpreter::Impl` 的实际
   成员比对（新增成员未注册 → 编译期或测试期失败）；每张表一个
   "唯一引用在侧表内 → GC 后存活"夹具（§11）。

## 9. 可观测性

- 结构化日志域 `runtime.dexvm.gc`（沿用限流与环形缓冲，禁止裸输出）：
  每轮输出 `{trigger, live_bytes, freed_bytes, live_objects,
  freed_objects, host_destructors_run, pause_ticks}`。
- `InterpreterStats` 扩展：GC 次数、累计回收字节、峰值水位。
- `dexvm.stats` 查询面（04 §8 规划）落地时直接吸收上述字段；本批次
  先保证 stats 结构体可查，closed-schema 查询面不在本批次范围。

## 11. 验证体系

全部机器可判定，dexasm 夹具 + doctest，进 `tests/dexvm/gc_tests.cpp`：

- **回收正例**：解释执行分配一批对象后断开全部引用（寄存器覆写 +
  字段清空），触发 GC，断言 `freed_objects`/`allocated_bytes` 精确
  下降、store `Delete` 生效（store Length 查询明确失败）、句柄空闲后
  `At()` 明确失败。
- **根覆盖一票否决矩阵**：每个根类别一个夹具——垃圾候选对象仅由该
  根引用（帧寄存器 / `last_result` / pending exception / 静态 ref 槽 /
  JNI local / JNI global / intern / Thread 对象 / 每张侧表），GC 后
  断言存活且值不变。任何一个根枚举被遗漏，对应夹具必然失败。
- **弱语义**：JNI weak global 指向的对象仅剩 weak 引用 → GC 后解析
  返回 null（`ClearWeakReferencesTo` 路径）；`WeakReference` intrinsic
  的 referent 有强引用语义（GC 后 `get()` 仍返回，按 §1 非目标记账）。
- **宿主析构**：声明了 `HostStateDestructor` 的 host_backed 对象死亡
  → handler 恰好调用一次（计数器断言）；存活对象绝不触发。
- **触发与 OOM**：水位夹具（预算调小，分配流精确越过阈值 → GC 在
  预期分配点发生，`InterpreterStats` GC 次数断言）；回收后仍不足 →
  真实 OOM 且 message 可判定；`gc_watermark_percent = 0` → 行为
  逐位回到 GC-A（关闭即失败：上述回收夹具在此配置下必须失败）。
- **句柄复用**：回收后新分配复用空闲句柄（句柄值断言）；复用前
  悬垂访问明确失败。
- **幂等与不朽**：连续两轮 GC 第二轮 `freed_objects == 0`；interned
  字符串与 class 对象在任何轮次后存活。
- **确定性**：同一夹具跑两遍，GC 触发点、句柄序列、stats 逐位一致。
- **exact-title gate（唯一真实出口，05 §4 规则不变）**：A5
  `title_flow`、A6 `bootstrap`、DH 启动 Scenario 三轮持平（GC 开启
  不得改变任何 golden）；随后新增一条长运行 Scenario 断言 GC 至少
  发生一次且水位回落——这是 `dexvm.gc` 状态推进的门槛。
- **能力账本**：`dexvm.gc` 在 §12 批次全部交付且长运行 gate 通过后
  `partial → complete`；quirk/参数条目同步 `capabilities.toml`。

## 12. WU 分批（批次 5 · GC-B）

创建任务单时在 `docs/tasks/dexvm/README.md` 按现行序号续编
（DVM-40 起），每个 WU 单会话可完成、依赖显式：

| WU | 一句话目标 | 关键交付 | 机器可判定验收 |
| --- | --- | --- | --- |
| GC-B-1 根枚举 | 不回收任何东西，先把全部根类别枚举成可测试的 `RootVisitor` 面 | `JniReferenceTable::VisitRoots`、静态 ref 槽预计算、context/线程根枚举、侧表注册制（§8） | 根覆盖矩阵的"枚举计数"版全绿；full CTest 无回归 |
| GC-B-2 标记器 | 从根出发精确标记，只统计不清扫 | mark 位 + 灰栈 + 逐 kind 扫描 + 侧表 trace hook；stats 曝光 live/garbage 字节 | 可达性夹具（活/死对象矩阵的标记结果断言）；关闭时零开销 |
| GC-B-3 清扫器 | 把未标记记录真实回收并复用句柄 | 三条空闲链、store `Delete`、表清理、`reserved_bytes` 回减、`At()` 空闲防御 | 回收正例 + 句柄复用 + 幂等夹具；`allocated_bytes` 双向 |
| GC-B-4 宿主析构 | host_backed 死亡释放宿主资源 | `IntrinsicClassBuilder::HostStateDestructor` + 现有需释放资源的 intrinsic 类逐个声明 | 析构恰一次夹具；未声明类行为不变 |
| GC-B-5 触发接线 | 水位触发、OOM 前最后一搏、profile 参数 | 安全分配点触发检查、`gc_watermark_percent` schema + 校验器、`System.gc` 注释更新 | 触发/OOM/关闭即失败/确定性夹具 |
| GC-B-6 gate 复验 | title 无回归 + 长运行水位有界，能力推进 | A5/A6/DH 三轮持平；长运行 Scenario；`dexvm.gc → complete`；`MODULE.md`/`CURRENT.md`/账本同步 | 三 gate 通过 + 长运行断言 + 账本单调推进 |

依赖链：1 → 2 → 3 → {4, 5} → 6。GC-B-1/2 完全不改变运行行为，可与
其他工作并行落地；行为开关从 GC-B-5 起才存在。

## 13. 风险表

| 风险 | 缓解 |
| --- | --- |
| 根枚举遗漏 → 活对象被清（最严重故障形态） | §11 一票否决矩阵每根一夹具；`At()` 空闲防御把悬垂从静默别名变成硬失败；GC-B-2 先以"只标记不清扫"上线观察 live 统计 |
| 宿主代码裸存 `JniObjectIdentity` 不经 global ref → 清扫后悬垂 | 既有契约本就禁止；`FromIdentity` 对已清扫身份重新登记为 external ghost 的路径加记账日志，长运行 gate 观察；发现即修调用方 |
| intrinsic 在两个安全点之间分配超过预算余量 → 过早 OOM | 余量默认 128 MiB 量级；OOM message 携带水位与余量诊断，命中即调 `gc_watermark_percent` quirk（受检参数，关闭即失败测试兜底） |
| 句柄复用扰动依赖 identity hash 的解释代码 → 行为漂移 | 与真机地址复用同构（§6 裁决）；exact gate 三轮比对是最终裁判，漂移即回退调查 |
| GC 暂停拉长单帧 | STW 全量回收的已知代价；暂停 tick 进日志与 stats，超预算按 06 §3 性能纪律先采样后优化（增量化是显式的后续 ADR，不在本批次） |
| 新侧表/新 intrinsic 忘记注册 trace hook | §8 注册制装配期失败 + 枚举比对测试，不依赖人记忆 |
