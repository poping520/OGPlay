# 00 · 目标、范围与非目标

---

## 1. 一句话定位

> 一个跨平台的**安卓老游戏兼容层**：翻译 ARM 机器码，用宿主原生实现扮演 Android，
> 让 2010–2016 年的安卓游戏在今天的 Windows / Linux / macOS 上原样运行。

**它不是 Android 模拟器。** 没有 Android 系统、没有虚拟机镜像、没有开机过程。

---

## 2. 为什么做这件事

- 这批游戏正在消失：厂商下架、服务器关停、新系统不再兼容旧 ABI、32 位应用被淘汰。
- 现有方案都不合适：完整 Android 模拟器（BlueStacks/Waydroid）重、慢、且同样受
  "旧应用在新 Android 上跑不起来"的限制；单游戏移植项目不可复用。
- HLE 路线在同类领域已被验证：touchHLE（iPhone OS 应用）、
  PvZ2Native / Bogodroid / Android Translation Layer（安卓单游戏或单平台）
  都走通了原理，但都停在"少数游戏"或"单一平台"。**通用 + 跨平台 + 可持续维护
  是空白。**

---

## 3. 目标

### 3.1 必达

| # | 目标 | 验收 |
| --- | --- | --- |
| G1 | 三平台原生运行 | Windows / Linux / macOS 各有可用发行版，功能一致 |
| G2 | 通用性 | 新增一个游戏 = 加一份数据文件，不改代码（见 [05](05-title-profiles.md)） |
| G3 | 三个 Android 版本 | 内置 4.4 / 5.1 / 7.1 的 Bionic，按游戏选择 |
| G4 | 完整 JNI | JNIEnv 全表实现 |
| G5 | AI 可持续开发 | 有制度化的流程与可机器判定的验收（见 [02](02-ai-workflow.md)） |
| G6 | AI 可操控调试 | Agent Control API + MCP（见 [03](03-agent-interface.md)） |
| G7 | 资源导入体验 | 用户丢进任意结构的游戏包即可运行（见 [06](06-user-experience.md)） |
| G8 | 键鼠/手柄可玩 | 含重力感应模拟与屏幕映射编辑器 |
| G9 | 完善的日志与诊断 | 结构化日志、地址自动符号化、崩溃诊断包（见 [09](09-logging.md)） |

### 3.2 期望

- 即时存档 / 快进
- 超采样渲染（提升老游戏画质）
- 公开的兼容性题库与社区贡献流程

---

## 4. 非目标（同等重要）

**明确不做的事，是这个项目能做完的前提。**

| 不做 | 理由 |
| --- | --- |
| 完整 Android 系统 / 四大组件 / PackageManager | 做了就是 Android 模拟器 |
| binder / IPC / system_server / Zygote | 游戏进程内不会直接用 |
| 现代应用兼容（社交、支付、反作弊、Play 服务） | 目标是游戏，且是老游戏 |
| Google Play / 账号 / 云存档 / 联网对战 | 服务器多已关停；默认离线 |
| 完整 ART/Dalvik JIT | 只在需要时做解释器，且只跑游戏自有类（见 [04 · 7](04-android-runtime.md)） |
| Vulkan / RenderScript / MediaCodec 全格式 | 老游戏用不到 |
| 手机端运行（Android/iOS 版模拟器） | 首版不考虑，架构上不排斥 |

**范围判定准则**：这个 API，**游戏进程自己**会调用吗？会 → 做；只有系统服务会调 → 不做。

---

## 5. 目标游戏画像

- 年代：2010–2016
- 形态：NDK 原生游戏为主（`lib/armeabi-v7a/*.so`），Java 层薄
- 引擎：厂商自研 C++ 引擎（Gameloft/EA/Glu）、Unreal Engine 3、Cocos2d-x、
  Unity 3.x/4.x、Corona
- 明确纳入但优先级靠后：libGDX / AndEngine 等 Java 厚层游戏（依赖 DEX 执行，
  按 [04 · 7](04-android-runtime.md) 的数据决定投入）

---

## 6. 成功标准

项目做到什么程度算成功：

1. **题库通过率**：内置题库中 Playable 及以上比例 ≥ 70%
2. **通用性**：新游戏适配的中位工作量 = 一份 profile，不改代码
3. **可持续性**：一个新接手的 AI 会话，能在读完 `AGENTS.md` + `CURRENT.md` +
   相关 `MODULE.md` 之后直接开始有效工作，不需要人类补充上下文
4. **可回归**：任何一次提交都会跑完整题库回归，兼容性等级只升不降

## 7. 风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 范围蔓延成 Android 模拟器 | 永远做不完 | 第 4 节的非目标清单写进 `AGENTS.md`，每个 WU 评审时对照 |
| AI 长周期开发导致架构腐化 | 不可维护 | [02](02-ai-workflow.md) 的全套机制，尤其 ADR + 能力账本 + quirk 强制测试 |
| 兼容性长尾无穷无尽 | 投入无底洞 | 题库驱动，按"影响游戏数"排优先级，不追单个游戏 |
| 图形层重蹈手写 GLES 的覆辙 | 大量静默 bug | 改用 ANGLE，语义交给它保证 |
| 线程模型（协作式）撑不住真实游戏 | 大面积时序 bug | 一开始就上真线程，见 [04 · 4.3](04-android-runtime.md) |
| 法律：系统库再分发 | 发行受阻 | 只用 Apache-2.0 的 AOSP 产物，完整标注来源与许可；不分发任何游戏内容 |
| 法律：商标 | 改名成本 | 命名避开 Android/Droid，见 [08](08-naming.md) |

## 8. 与 DEMO 的关系

DEMO（当前 17,146 行代码）的价值**不在代码，在已验证的知识**：

- 哪些 Android API 是这类游戏真正会用的（已绑定约 289 个 libc 符号、153 个 GL 入口）
- 每个子系统的坑长什么样——这些已经提炼成设计约束，写在
  [01 · 6 已知失效模式](01-architecture.md)
- **Asphalt 6 可进主界面并响应交互**，证明整条 HLE 路线可行

现有四个游戏的适配进度并不一致，需要如实记录：

| 游戏 | 状态 |
| --- | --- |
| Asphalt 6 | 可进主界面，可交互 |
| Dungeon Hunter | 可进菜单 |
| Asphalt 5 | 有独立启动路径 |
| Tales From Deep Space | **尚未跑通** |

Tales From Deep Space 是项目最早的目标（也是旧名 TalesHLE 的由来），但至今没有跑通。
它用 Frontier 自研引擎 + Lua + FMV，Java 层也更厚，是四个里最难的一个。
正式版不应急于让它跑起来，而应等运行时能力（真线程、完整 JNI、syscall）补齐后
再作为**通用性的检验题**回过头来处理。

正式版是**重写内核 + 迁移知识**，而不是在 DEMO 上继续叠加。
DEMO 继续保留可运行，作为新实现的对照基准。
