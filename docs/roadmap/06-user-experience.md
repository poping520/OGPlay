本篇回答需求 4.1、4.2。

## 1. 游戏资源的发现与导入（4.1）

### 1.1 问题有多杂

老游戏的数据外置方式没有统一标准，实际见过的形态：

| 形态 | 例子 |
| --- | --- |
| 标准 OBB | `/Android/obb/<pkg>/main.<ver>.<pkg>.obb`（zip，可能不压缩） |
| 应用外部目录 | `/Android/data/<pkg>/files/` |
| 厂商自定义目录 | `/sdcard/gameloft/games/GloftAPHP/`、`/sdcard/EA/`、`/sdcard/glu/` |
| APK 内 assets | 小体积游戏 |
| 首启动联网下载 | 现在服务器早已关停，只能靠用户提供离线包 |
| 打包分发格式 | XAPK / APKM / APKS（内含 APK + OBB + 目录树） |

用户拿到的往往是一个"从某处下载的压缩包"，里面结构千奇百怪。**如果让用户自己搞清楚
文件该放哪，这个模拟器就没法用。**

### 1.2 方案：导入向导 + 内容寻址存储

```
用户拖入：APK / XAPK / 文件夹 / zip
              │
              ▼
     ┌──────────────────┐
     │ 识别：包名、版本、 │  ← 解析 AndroidManifest + .so 指纹
     │      引擎、ABI    │
     └────────┬─────────┘
              ▼
     ┌──────────────────┐
     │ 匹配 Title Profile│  ← 内置题库，含"该游戏需要哪些数据"的清单
     └────────┬─────────┘
              ▼
     ┌──────────────────┐
     │ 扫描并归位数据     │  ← 递归扫描用户给的任意目录结构，按特征文件识别
     └────────┬─────────┘
              ▼
     ┌──────────────────┐
     │ 校验并报告缺失     │  ← 明确告诉用户"还缺 main.7.obb"
     └──────────────────┘
```

关键设计：

1. **不要求用户还原 Android 目录结构。** 用户给一个乱七八糟的文件夹，我们递归扫描，
   按特征文件（`main.*.obb`、`*.dat`、`intro.mp4`…）识别并建立映射。
2. **Title Profile 里带"数据清单"**：期望的文件/目录、大小范围、可选必需标记。
   导入完立刻能回答"能不能跑"。
3. **每个游戏一个独立的虚拟 sdcard**，存档互不干扰，也便于备份与迁移。
4. **不复制大文件**：OBB 等只读大包直接原地挂载（`fs.map` 里做路径重定向），
   不做几百 MB 的拷贝。
5. **缺文件时给可执行的提示**，而不是"初始化失败"。配合
   `fs.missing()`（见 [03](03-agent-interface.md)）把 guest 实际找过、但不存在的路径直接列给用户。

### 1.3 跨平台的坑

- **大小写敏感性**：Android 是大小写敏感的，Windows / macOS 默认不敏感。
  老游戏里 `Loading02.TGA` 与 `Loading02.tga` 混用是常态。
  → VFS 必须自建**大小写不敏感的索引**，并在命中不精确匹配时记录警告。
- **路径长度**：Windows 的 260 字符限制，OBB 内深层路径会踩。
- **文件名非法字符**：`:` `?` `*` 在 Windows 非法，需要转义层。
- **符号链接**：Windows 上需要管理员权限，避免依赖。

## 2. 输入：把触屏游戏变成能用键鼠/手柄玩（4.2）

### 2.1 输入源与目标的映射矩阵

```
输入源                        虚拟设备
──────────────────────────    ────────────────
鼠标                     ┐
键盘                     ├──► 触摸屏（多点）
手柄（SDL GameController）┘    ├─► 加速度计 / 陀螺仪
                               ├─► 物理按键（Back/Menu/Volume）
                               └─► 轨迹球（少数老游戏）
```

### 2.2 分层设计

**第一层：设备抽象。** 统一成事件流，源无关。

**第二层：映射引擎。** 由 Title Profile 提供，可被用户覆盖：

```toml
[[input.binding]]
source = "key:W"
target = "touch"
zone   = "accelerate"        # 引用下面定义的屏幕区域

[[input.binding]]
source = "gamepad:left_stick_x"
target = "sensor:accelerometer_x"    # 赛车类倾斜转向
curve  = "linear"; deadzone = 0.15

[[input.zone]]
name = "accelerate"; shape = "rect"; rect = [1100, 560, 180, 140]
```

**第三层：屏幕叠加编辑器。** 用户在游戏画面上直接框选按钮位置并绑定按键——
这是唯一能让普通用户搞定任意游戏的方式。做得好的话，社区可以共享映射配置。

### 2.3 必须做对的几件事

1. **加速度计不是可选项。** Asphalt 系列、极品飞车、Doodle Jump 这类游戏的主操作
   就是重力感应。必须能用手柄摇杆/键盘平滑地模拟倾斜，带死区和回中曲线。
2. **多点触控合成。** 缩放/双指旋转要能用"修饰键 + 鼠标"完成。
3. **触摸的时序语义。** 很多引擎要求 down/up 成对并间隔若干帧；点击、长按、拖拽、
   轻扫要分别建模，不能只发一对 down/up。
4. **鼠标锁定模式。** FPS/第三人称游戏需要相对移动而非绝对坐标。
5. **手柄数据库。** 直接用 SDL 的 GameController 映射库，别自己维护。
6. **默认映射要能自动生成。** 结合 Title Profile 里的按钮区域标注，
   新游戏第一次运行就有一套能玩的默认键位，而不是一片空白。

### 2.4 显示适配

老游戏分辨率固定（800×480、1280×720 居多）且大量硬编码 UI 坐标。

- 默认**整数倍/等比缩放 + 黑边**，保证 UI 不错位
- 提供"拉伸填充"和"裁切填充"选项，但标注可能导致 UI 溢出
- 支持自定义渲染分辨率（部分 3D 游戏可超采样出更好画质，需按题标注是否安全）
- 处理 UI 安全区与鼠标坐标的换算，**逻辑坐标与物理坐标的换算必须只有一处实现**
  （DEMO 阶段这里已经出过 1.25 倍的错）

## 3. 前端

### 3.1 形态

- **CLI**（`armature run <apk>`）：CI、脚本、AI 使用
- **GUI**：游戏库 / 导入向导 / 每游戏设置 / 输入映射编辑器 / 兼容性状态
- 二者共用同一个内核库与配置，GUI 不得有内核里没有的行为

技术选型建议：GUI 用 Qt 6（跨三平台成熟、无 Web 运行时负担），
或 Dear ImGui（更轻，但复杂表单体验差）。倾向 **Qt 6**。

### 3.2 兼容性可见性

游戏库里每个条目显示分级状态，数据来自题库回归 CI，而不是手填：

| 等级 | 含义 |
| --- | --- |
| Perfect | 可完整通关，无明显问题 |
| Playable | 可玩，有小瑕疵 |
| Menu | 能进主菜单，进不去游戏 |
| Boot | 能启动，画面异常 |
| Broken | 崩溃 |

touchHLE 的做法（公开的 app 兼容性数据库）值得直接借鉴。

### 3.3 其他体验点

- **存档管理**：导入/导出/备份，独立于游戏数据
- **即时存档（Save State）**：技术上等价于快照整个 guest 状态，
  对老游戏体验提升巨大；架构上要求内存/CPU/GPU 状态可序列化，**需要在设计期就考虑**，
  后补代价极高
- **快进/慢放**：统一时钟已有，前端暴露即可
- **首次运行诊断**：自动跑 5 秒并报告"GPU 后端 / 缺失文件 / 已知问题"
- **崩溃报告**：自动附上符号化的 guest 调用栈、`hle.unimplemented()` 列表、
  GPU 后端信息——用户提交的 issue 质量直接决定修复效率
