# 07 · 开发路线图

里程碑按**依赖关系**排序，不按日历。每个里程碑都有可机器判定的出口条件。

---

## 总览

```
M0 工程地基 ─► M1 内核与跨平台 ─► M2 Bionic + Syscall ─► M3 JNI + 框架 ─► M4 图形栈
                                                                          │
M8 兼容性冲刺 ◄─ M7 用户体验 ◄─ M6 AI 自动化测试 ◄─ M5 去硬编码 ◄──────────┘

M9 DEX 解释执行：条件触发，可独立插入
```

## M0 · 工程地基

**这一步不写模拟器功能，只建能让 AI 长期开发的地基。跳过它，后面全部失控。**

| 任务 | 出口条件 |
| --- | --- |
| `AGENTS.md` + `docs/` 结构 + `CURRENT.md` 交接协议 | 新会话能靠文档自举 |
| ADR 机制启动，把已做的关键决策补录 | ADR-0001..N 存在 |
| 按模块职责拆分三个巨型文件 | 依赖边界清晰，修改无需跨无关职责 |
| **结构化日志系统**（[09](09-logging.md)） | 275 处裸输出清零；CI 禁止 `printf`/`cerr`；地址自动符号化；环形缓冲可转储 |
| CMake + vcpkg/Conan 三平台构建骨架 | 三平台 CI 均能编译 |
| 测试框架换 Catch2/doctest + CI | `ctest` 跑通 |
| 黄金帧测试基础设施（含软件渲染后端） | 无 GPU 环境可跑画面回归 |
| `capabilities.toml` + 运行时 unimplemented 计数 | 账本可查 |
| Agent Control Server 最小版（`session`/`run`/`sym`/`hle`） | AI 能用接口跑通一次调试 |

> **`sym.resolve` 优先做**：它消除的是当前最大的人工浪费（手动开 IDA 查地址）。

## M1 · 内核与跨平台

| 任务 | 出口条件 |
| --- | --- |
| HAL 抽象（window/gfx/audio/input/fs/clock/thread） | `src/` 中平台相关代码全部在 `hal/<platform>/` 下 |
| 窗口/输入换 SDL3 | 三平台窗口生命周期与输入映射契约测试通过 |
| 内存：4 GiB 直接映射 + 宿主权限 + soft-MMU 调试模式 | 映射、权限、fault、观察器与快照契约测试通过 |
| CPU：Dynarmic A32/T32；解释器参考后端 | M1 裸样本的指令级结果在两后端一致 |
| 真线程模型 + futex | 多线程压力测试通过 |
| 统一时钟（实时/固定步长/快进/暂停） | 确定性回放可复现 |
| 状态快照骨架 | 能存/读一个最小 guest 状态 |

**出口**：A32 与 Thumb 裸 guest 样本（不依赖 APK、ELF、Bionic、JNI、EGL/GLES）
在三平台的解释器和 JIT 后端产生一致结果；样本能读取宿主注入的标准化输入并写回
确定性状态。M1 不要求画面，窗口/输入 HAL、线程、时钟分别通过各自契约测试。

## M2 · Bionic 与 Syscall

| 任务 | 出口条件 |
| --- | --- |
| 完整 ELF linker（含 `dlopen`/符号版本/TLS/exidx） | 多层依赖的 `.so` 能正确加载 |
| 装载真实 AOSP Bionic（API 19/22/23） | 三版本各自通过 libc 自检 |
| 选择性拦截（mem 函数热点；pthread/mmap syscall；log 边界） | 行为与性能基准达标 |
| Syscall 层（约 120 个，按组） | 未实现 syscall 100% 可观测，绝不静默成功 |
| VFS：APK/OBB/外置统一，大小写不敏感索引 | 跨平台路径测试通过 |

**出口**：一个导出普通 C 入口、使用 pthread + 文件 IO + malloc 的无界面 NDK `.so`
完全正确运行，不依赖 Activity、JNI 或 GLES。

## M3 · JNI 与 Java 框架

| 任务 | 出口条件 |
| --- | --- |
| JNIEnv 233 槽 ABI + JavaVM；常用函数优先实现 | 已实现函数契约全覆盖，其余槽 100% 可观测并 trap |
| 引用表（Local/Global/Weak）+ 异常状态机 | 溢出与异常语义符合真机 |
| 签名解析器 + 三种调用变体 | 描述符测试集通过 |
| Modified UTF-8 正确处理 | 中日文文本测试通过 |
| Java 框架 HLE 声明式绑定表 | `android.*` 常用类可用 |
| DEX L1（只解析不执行） | 能输出引擎指纹与 Java 厚度报告 |

**出口**：通用生命周期模板驱动的无界面 JNI 契约样本完成 Java/HLE ↔ native 双向调用、
引用与异常闭环；图形和音频只验证边界契约，不以真实 present 作为本阶段出口。

## M4 · 图形栈

| 任务 | 出口条件 |
| --- | --- |
| 接入 ANGLE，EGL 完整实现 | 三平台各自选到合适后端 |
| GLES 边界库由 IDL 生成 | GLES 1.1 / 2.0 全覆盖，3.x 按需 |
| GL 资源与 guest 内存的搬运层 | 无手写 per-function 代码 |
| `gpu.*` Agent 接口 | 帧统计、渲染目标、能力、trace 可查 |
| 显示适配（缩放/黑边/超采样） | UI 不错位 |

**出口**：最小 NativeActivity NDK APK 在三平台跑出画面并响应输入；GLES2 一致性样例
通过，黄金帧测试在软件后端稳定。

## M5 · 去硬编码机制与 exact-title bring-up

M5 在 `WU-0199..0327` 共形成 129 个 Work Unit。为避免继续扩大单一里程碑上下文，
历史任务保持原编号和目录不动，并按 [`docs/tasks/m5/README.md`](../tasks/m5/README.md)
拆成三个只读交付批次；M5 的能力开发范围冻结在 `WU-0327`，后续新任务从 M6 开始。

| 任务 | 出口条件 |
| --- | --- |
| M5-A：Profile、Quirk、APK 身份与启动计划（WU-0199..0223） | Profile 保持纯数据，三重身份匹配不猜测，装配失败不发布部分计划 |
| M5-B：首个 exact title 的 guest ABI 与 GLES bring-up（WU-0224..0276） | Profile 驱动统一 guest session；JNI/GLES 缺口可查询并明确失败 |
| M5-C：音频、输入、第二 title 与长帧生命周期收敛（WU-0277..0327） | 编码声音经真实解码/混音/SDL 输出；窗口、输入和 lifecycle 保持通用编排 |
| 生产代码去标题特判 | `grep -ri "asphalt\|gameloft\|dungeon\|fCoreJava" src/` 为空；每个 Profile ≤ 200 行 |

**出口**：通用 Profile 路径能够以精确 APK 身份完成受检启动、guest 调用、画面、输入、
声音和生命周期闭环，且生产代码零游戏特判。M5 的正式验收只汇总既有 WU 的机器证据；
不得为了补验收继续向 M5 追加能力 WU。

> A6 / DH / A5 的完整主界面、交互、声音题库回归移入 M8，由 M6 建成的自动化执行层
> 判定，不再依赖人工观看。Tales From Deep Space 仍只在 M8 作为通用性检验题。

## M6 · AI 自动化测试

详细契约见 [10 · AI 自动化测试](10-ai-automation-testing.md)。

| 任务 | 出口条件 |
| --- | --- |
| exact-APK 场景与检查点 schema | 场景为受检纯数据；APK/外部资源不进入仓库 |
| Profile-backed Agent session | `session/run/input/frame/gpu/hle/fs` 读取同一真实 guest 会话 |
| 确定性、有界执行 | 每个动作有 guest frame/tick/wall-time 上限，超限明确失败 |
| frame capture/readback 与黄金帧断言 | 像素差、感知哈希和差分图可机器判定 |
| 结构化结果与证据包 | JSON 结果含身份、动作、断言、首个失败、日志、能力命中和末帧 |
| 首个 title 端到端场景 | exact APK 完成启动→输入→检查点→正常退出，连续三次结果一致 |

**出口**：AI 和 CI 使用同一个非交互 runner，在不解析自由文本日志、不依赖人工点击或
人工看图的前提下，对至少一个 exact APK 完成有界场景并生成可复核证据包；任何缺失
fixture、未实现查询、超时或断言失败均 fail closed。

## M8 · 兼容性冲刺

- 批量跑题库，按"影响游戏数"排序补 API，而不是追单个游戏
- 每个新支持的游戏产出一份 profile + 一条题库回归
- A6 / DH / A5 在新架构上达到与 DEMO 同等或更好的画面、输入和真实声音表现
- **Tales From Deep Space 在此阶段处理**，作为通用性检验题：
  如果它需要的不止一份 profile，说明通用机制还有缺口，应回头补机制
- 公开兼容性数据库
- **目标：Playable 及以上 ≥ 70%**

## M9 · DEX 解释执行（条件触发）

**触发条件**：M4 之后用 DEX L1 的扫描数据复盘——

- 需要 DEX 的题目占比 **< 10%** → 不做，或只做到 L1
- **10%–25%** → 降优先级，M8 之后再评估
- **> 25%** → 立项，作为独立里程碑

内容见 [04 · 7.3](04-android-runtime.md)：DEX 解析、字节码解释器、对象模型与 GC、
内建类库、与 JNI 双向互通。**不做 JIT。**

---

## 并行与顺序约束

- **M0 必须最先完成**，且不可与其他里程碑并行——它定义了后续所有工作的方式。
- M1 与 M2 有强依赖（内存/线程 → syscall），不可换序。
- M3 与 M4 可并行（不同子系统，接口在 M1 已定）。
- M5 依赖 M2/M3/M4 全部完成，因为它要验证的正是"通用机制是否够用"。
- M6 复用 M5 的 exact Profile 启动路径；自动化 runner 不得复制第二套运行时。
- M7 可从 M4 之后提前启动 GUI 骨架，但用户界面不得成为 M6 自动化的依赖。
- M8 以 M6 的题库 runner 为前置条件，禁止重新退回人工 smoke 驱动兼容性开发。
- M9 独立，随时可插入。
