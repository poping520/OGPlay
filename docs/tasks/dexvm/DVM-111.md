# DVM-111 · JNI 对象数组的接口可赋值关系

## 目标与依赖

依赖 DVM-110（d283144d），修复真实 JNI 桥下定时任务写入接口数组被误拒绝的问题。

## 复现与计划

用户原命令启动 PvZ，日志 `.local/review/dvm111/before.log`；增加类型诊断后确认：
`ScheduledThreadPoolExecutor$ScheduledFutureTask -> RunnableScheduledFuture` 被拒绝。
原版 DelayedWorkQueue 使用接口数组；JNI registry 只保存父类链，旧 VM 类型回调仅用于
synthetic 数组类，普通类实现接口的写入遗漏了 VM 判断。

1. 将数组类型回调扩展到 VM 已知普通类/接口，保持无 VM 元数据时的原有严格校验。
2. 在真实 session/JNI bridge 下回归 schedule/队列、接口继承、拒绝写入与 GC；双后端受检。
3. 定向回归 JNI 数组、嵌套数组与定时器，原命令复跑并记录下一停止点。
4. 同步 MODULE、能力和 CURRENT，不修改游戏 Profile，不提交 bootdex.jar/临时设备库。

## 验收

- [x] 回调保持数组锁外执行、VM 执行锁保护、线程停止后撤销。
- [x] 合法接口写入通过，非法写入保持原元素；无 VM metadata 仍严格校验。
- [x] 双后端真实桥下 schedule 回归与相关定向测试通过。
- [x] 原命令复跑越过首错，记录实际结果；不将探索运行算作游戏 gate。

状态：完成。沿用现有显式回调与唯一 VM 类型事实，不在 JNI 复制接口表。
AOSP 依据：`libcore/luni/.../ScheduledThreadPoolExecutor.java` 的 ScheduledFutureTask/
DelayedWorkQueue，以及 `dalvik/vm/oo/TypeCheck.cpp` 的 dvmCanPutArrayElement/isInstanceof。

## 实现与验证（2026-09-08，macOS Release）

SetAssignability 返回 optional bool：VM 已知类型的 true/false 为最终结果；任一类型
未映射到 VM 时返回 nullopt，沿用 host registry 父类链或 synthetic 严格身份比较。
New 的 initial 与 Set 共用校验，错误包含源/目标类名或 synthetic class ID。

新桥接测试在修复前失败，错误与游戏完全一致，见 `red.log`。修复后覆盖双后端真实
schedule 入队、接口多级继承、native initial/set、非法写入保留原元素、host-only 类型
回退、GC 后读取和 shutdownNow 返回队列；回调单测还验证锁外重入与 false 不可被回退覆盖。

18 个定向用例、2860 断言通过（接口数组、定时器、原对象数组继承、Certificate、对象流）；
JNI ABI 29 用例、434 断言通过，共 47 用例、3294 断言，3 项门禁通过。仅构建 ogplay_tests/ogplay 依赖，

## 后续缺口分析：ServiceConnection（2026-09-08）

2026-09-08 对照 APK 方法字节和本地 AOSP：当前 new-instance 首错发生在创建回调对象时。
后续 startSetup 先 resolveService(intent, 0)，返回 null 则记录日志、清空 mServiceConn 并
返回；不会调用 bindService、onServiceConnected 或 onIabSetupFinished，mSetupDone 保持
false。辅助反汇编见 `.local/review/dvm111/service-setup.dex.txt`。这只证明该初始化方法
有服务缺失分支，后续游戏行为仍需原命令验证。

推荐下一 WU：ServiceConnection 原版接口选入 BootDex，同时补有事实依据的服务查询
未匹配结果。接口只有 onServiceConnected(ComponentName, IBinder) 与
onServiceDisconnected(ComponentName)，两个签名依赖已有类型，无需执行 Binder transport。

- ServiceConnection 加入现有 api19.json 的 framework.jar 清单，沿用统一构建器。
- PackageManager.resolveService 保留平台 intrinsic：AOSP API 19 在无匹配服务时返回 null。
  当前 ManifestFacts 只收集 Activity/alias，需补当前 APK 的 service 声明、enabled 和过滤器
  判定所需事实并注入 context。当前启动 Intent 只有 action、flags=0；先闭合这一有界查询。
  查询空间为当前 APK 与明确登记的平台服务；未安装的外部服务不构造 ResolveInfo。
- 确认无候选才返回 null；潜在匹配、未知 flags/不支持的过滤条件等不能判定的情况须
  记账并抛明确 Java 异常，禁止按游戏包名/action 特判或无条件返回 null。
- 本路径不必实现 bindService/unbindService、完整 ResolveInfo/ServiceInfo 家族、Binder/
  IInterface/支付服务。返回值类型和未执行正分支的元数据需求在链接测试中单独验证；
  不因为 DEX 常量池存在引用就迁入整个依赖树。

验收应覆盖：接口方法/access flags 与 APK 实现类链接；双后端查询无匹配、潜在匹配明确失败、
非法参数/flags；无服务时不回调、不产生绑定状态；最后原命令复跑。仅查无结果不等于
完整服务发现或服务生命周期支持。本轮只分析与更新文档，未构建、测试或修改运行时代码。

实施结果见 [DVM-112](DVM-112.md)，本节保留分析时的范围与依据。
