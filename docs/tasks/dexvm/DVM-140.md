# DVM-140 · Intent.putExtras(Bundle)

## 目标与依赖

依赖 DVM-117，按本地 AOSP 4.4.4 Intent.java:6141 补齐 Bundle 合并入口。

## 交付

- 复用 ensure_extras/mExtras，调用 BootDex Bundle.putAll 后返回 this。
- 独立键值映射、同名覆盖、值对象身份保留；无新类型分支或侧表。
- null 参数由原版 Java 抛 NPE，保留先创建目标空 Bundle 的顺序。
- 不迁移整个 Intent，不扩展 Binder/广播服务，不修改 BootDex。

## 验证

- 双解释后端覆盖空 Bundle、合并/跨类型覆盖、旧键保留、浅复制与 GC、null 值和
  null 参数异常及异常后的 extras 状态。
- Release ogplay/ogplay_tests 构建成功；DVM-140/DVM-117 定向 3 用例、414 断言通过。
- 原 PvZ 命令探索实跑越过 putExtras 缺口，第 1 帧新首错为
  `JNI guest receiver is not a registered instance`；未宣称完整游戏启动通过。

## 后续 JNI 故障分析（2026-09-09）

- 当前已验证修复提交 `6229ecda`（含 SBX-14，不含 BootDex）。
- exact 实跑临时 JNI 环形追踪：GetObjectArrayElement(1636,1) 返回 local ref 1638，
  随后 CallObjectMethodV(1638,1556) 调 entrySet()Ljava/util/Set; 失败。
  引用成功解析为 dex_vm identity 4508，但 JniGuestObjectRegistry.ClassOf 找不到它。
- JavaObjectModel::SetObjectArrayElement 已保存 object 与真实 java_class；
  GetObjectArrayElement 却只通过 Environment.PublishLocalObject 创建引用，
  未像 DexVmGuestBridge::PublishLocal 一样同步对象类型注册。
  因此数组本体进入 JNI 不等于所有子对象都已在 registry 登记。
- 修复应在对象发布路径利用已有真实类型完成幂等、一致性受检注册，不能用数组
  声明元素类型或 MethodID 所属类猜测 receiver 类型；保留严格 ClassOf 校验。
  回归覆盖 Java 新建 Map→Object[]→GetObjectArrayElement→entrySet、重复获取、
  GetObjectClass/IsInstanceOf 与 GC；并审计其他直接 PublishLocalObject 的出口。
- 本轮仅分析；临时诊断全部撤回，ogplay 重新构建成功。
