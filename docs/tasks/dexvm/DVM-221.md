## 已知像素语义问题与后续评估（暂缓）

记录日期：2026-10-07。用户要求先记录，暂不修复；本节不代表扩大已验收范围。

当前 `BitmapPixels` 是自研 C++ 实现，没有复用 Skia。未锁定时保存逻辑 ARGB，
首次 lock 才转换为 native 格式，最后 unlock 解码回逻辑 ARGB。因此，即使 native
未修改像素，单次 lock/unlock 也可能改变 Java 可见颜色。例如 `0x80010000` 经
当前预乘/反预乘公式变为 `0x80020000`；这是源码公式推导，尚未新增该用例的
机器回归。A8/RGB565/RGBA4444 同样存在延迟量化，锁定前后读写语义不一致。

后续修复方向：从创建/写入时就按固定物理格式存储，Java 与 native 共用唯一
像素 backing；lock/unlock 只管理访问及生命周期，避免因锁定新增格式转换。
这项修复不以引入 Skia 为前提。恢复工作时应补充无写入 lock/unlock 颜色不变、
各格式写入量化及 Java/native 互见的定向验证，并对照 API19 行为。

长期若扩充 BitmapFactory/Canvas 的缩放、滤波、混合、路径和文字能力，优先评估
固定版本的 Skia CPU 后端，减少自研图像算法；版本及 API19 像素格式/舍入兼容性
尚未选定或验证，引入 Skia 也不自动保证 API19 一致性。OGPlay 仍负责 JNI 引用、
guest 内存映射、锁、GC 和异常，GLES 继续使用 ANGLE。新依赖及架构变更另行
立项/记录 ADR；当前不引入依赖，也不替换实现。

另需评估整图转换/分配成本、完整颜色语义，以及线程、GC、recycle 和异常组合的
验证缺口。现有定向测试与 reached-fault 证据不能替代这些验收。
