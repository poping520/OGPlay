## 阶段 1 实现与约束

- `runtime/jni/java_payload.h` 定义强类型 handle/borrow、typed accessor、统计和 provider 接口；
  不依赖 AddressSpace 实现、DexVM、OS，不使用全局指针或 TLS owner。
- integration 实现 `GuestJavaPayloadProvider`。默认 16 KiB slab 是可配置的夹具初始参数，
  小块上限 slab/2、8-byte packed，大块单独按宿主 backing 粒度分配；从整个有效 guest
  范围 first-fit 扫真实映射账本，不占满 1 GiB、不另设固定地址堆。零长也有独立地址。
- 每块有 owner/generation；typed view 在创建时校验范围/对齐/所有权并保活 backing。
  每元素只做视图边界检查与直接字节访问，无 AddressSpace 锁、无存活原子探测、无裸 span。
  view/pin 活跃时 Release 明确失败；最后一个 view 退役前 provider 关闭也不拆映射。
  owner 串行化 view 构造与 Release，guest 使用完/CPU quiesce 后才能释放其块。
- 配额遵循 ADR-0060 initial target → growth limit，保留 maximum 的上界验证；logical allocated
  与 committed 分计，失败不改变目标或计数。当前仅夹具独立使用，阶段 2 必须接入现有 VM
  charge/GC context，不能形成两份生产堆账本。阶段 1 pin 仅接口/夹具验证，不接 JNI 借用。
- memory 登记 owner 和完整映射，修改检查/实际变更在同一锁内；munmap/mprotect、mremap
  原区/FIXED 目标及 MAP_FIXED 替换任何重叠返回 EPERM 并记账。普通 mremap 仍 ENOSYS。
  restore 在 owner 活跃时拒绝（包括尚未分配/释放全部块），base 保持稳定；AddressSpace 和
  ledger 必须晚于全部 view，且不能在 owner 活跃时移动 AddressSpace。
- payload 和普通 RW 非 X 页正常进入两张直接表，observer 行为不变；没有新增 guest
  并发承诺。checked-only 仅保留未来有实测依据时讨论诊断开关的可能。
- `JniPrimitiveArrayStore/JniStringStore`、DexVM 对象模型、jni_guest 与 NIO 源码均未修改。

### 保留的阶段 2 实现

primitive store 显式注入 provider，entry 保存 kind/length/handle/长期 typed view；生产

### 已确认根因与分配器设计

规划方对旧候选的 096 switch 在 `Starting the test` 后采样 8 秒，Allocate 自身占 **5,909**
个采样点，解释器约 200 个，其他线程在 execution lock 条件变量上等待（26,403 个）。
小块分配遍历全部 small arena，再逐位扫描 vector<bool>，耗时随 slab 数增长；分配期间
持 VM 执行锁，三个 Java 线程一起受阻。压力源是字符串拼接创建的小 char[]。

修复仅限分配/释放路径和聚合统计：

- **64 个尺寸级别**，8-byte 对齐；128 以内每 8 字节一级，此后每个翻倍区间 8 级。
  直接 lookup 共 1025 项，不按 slab 总数查询。默认级别表（字节）：

| 区间 | 槽大小 |
| --- | --- |
| 1..128 | 8, 16, 24, 32, 40, 48, 56, 64, 72, 80, 88, 96, 104, 112, 120, 128 |
| 129..256 | 144, 160, 176, 192, 208, 224, 240, 256 |
| 257..512 | 288, 320, 352, 384, 416, 448, 480, 512 |
| 513..1024 | 576, 640, 704, 768, 832, 896, 960, 1024 |
| 1025..2048 | 1152, 1280, 1408, 1536, 1664, 1792, 1920, 2048 |
| 2049..4096 | 2304, 2560, 2816, 3072, 3328, 3584, 3840, 4096 |
| 4097..8192 | 4608, 5120, 5632, 6144, 6656, 7168, 7680, 8192 |

- 请求 >128 B 的最坏槽内取整损失为 **511/4097 = 12.4725%**；1..128 B 最多补 7 B
  （1 B 请求为 700%），零长独占 8 B 槽，不用百分比描述。slab 尾部不足一槽的空间另计。
- 每个 16 KiB slab 仅服务一级，空闲槽栈最多 2048 项；各级用有空位 slab 的侵入链表，
  槽分配/归还和链表增删 O(1)。不逐位扫描，不遍历所有 slab。新 slab/缓存重分级的槽表
  初始化有最多 2048 项的固定上界；实际映射仍走统一 guest 账本 first-fit 慢路径。
- 全局最多缓存 **64 个空 slab（1 MiB）**，超额才 UnmapProtected；空 slab 可直接重分给
  其他级别，避免因错误级别缓存占满 committed 配额而无法分配。元数据先准备，再提交
  free list/cache/计数变化；分配后清零，generation、独立零长地址、保护映射和邻页合同不变。
- generation→Allocation 从 std::map 改为散列表，元数据增删由 O(log N) 改为摊还 O(1)；
  arena 所有权由 vector 改为稳定 list 节点，解除释放时的全表 erase_if。
- Block 的 make_shared、typed view Lifetime 分配及现有锁范围保留。下面的复采证明它们
  已不是主要热点，未继续进行固定开销优化。以上组合改动没有逐项独立计时，不作分别归因。
- committed/slab_free/峰值 live/长度分桶接口保留；新增每级 slot_bytes、slabs、total_slots、
  live_slots、累计 allocations 的只读快照与 Stop 结构化日志。slab_free 包含 slab 尾部空闲，
  不把已占用槽内的取整损失计作可用空槽。

### 061 根因与定位证据

修改前先在 `JavaObjectModel::NewPrimitiveArray` 的失败出口及 provider 失败出口加入临时
只读诊断（宿主栈、VM 账本、provider 统计），构建 CLI 并复现 061 switch。临时日志与
execinfo 代码随后完整撤回，不进入提交；原始日志为 `061-before-diagnostic.txt`、
`061-before.stderr`、`061-before.stdout`，修改前源文件副本也留在证据目录。

- **全例最早拒绝分配的是 VM**：huge-array 请求 int[1,073,741,828]，VM allocated=634、
  target=2,097,786 B；这属于用例预期 OOME。large-OOME 段同样已被正确捕获，不能把它们
  误称为 provider 首错。
- 小对象填堆期间出现 **provider 先于 VM 耗尽 backing**：第一个 provider 失败请求
  byte[18,888]，committed=**536,870,912 B**、slab_free=**49,016 B**、payload live=
  **536,802,028 B**。该次 Reserve 后实际 VM allocated=**536,868,182 B**，仍未超过
  target/growth=**536,870,912 B**；失败回滚后日志记录 allocated=**536,849,262 B**。
  因级别隔离、页取整与 slab 空闲，不能仅凭 slab_free 总数宣称该请求有可用 backing。
- 最终在构造 OOME 时再次失败的是 **int[12]，48 B payload**，调用栈为
  NewPrimitiveArray → CaptureThrowableStack → Throwable native stack capture →
  InitializeThrowable → MakeThrowable → ThrowJava → interpreter Run。此时 provider
  committed=536,870,912、slab_free=30,936、payload live=536,818,980 B；VM 已处于
  emergency=TRUE，回滚后 allocated=536,871,204、target=536,870,912、remaining=65,212 B。
  VM 应急账本有余量，但 provider 的独立 512 MiB 提交上限不识别 emergency，导致二次
  heap_budget_exhausted 触发 MakeThrowable 的递归保护。**规划推测在这一关键路径成立。**

### 修改与边界

- 生产取消固定 512 MiB provider 配额。VM 通过 store.ConfigurePayloadHeap 显式传
  maximum/growth；provider 根据实际 slab/backing 粒度推导普通提交上界，VM Reserve
  仍是唯一逻辑堆账本。公式为 min(VAS − E, F × maximum + C × S)，
  F=max(3, ceil(S/32))，S=slab bytes，C=空 slab 缓存上限，E=应急预留；使用饱和运算。
  3 覆盖级别取整/尾部/大块页取整，S/32 进一步覆盖每个 slab 只留一个零长数组的极端
  稀疏碎片，而不是假设所有 slab 都密集。默认 S=16 KiB，F=512，因此饱和到可映射 VAS；
  仅是安全上界，不预提交、不扩大 Java growth limit。实际 VAS/OS commit 仍可先失败。
  maximum 覆盖 VM 后续 clearGrowthLimit；0 < growth ≤ maximum ≤ 4 GiB 在入口验证。
- ConfigureHeap 预提交 **256 KiB** 独立受保护应急池，普通 Allocate 不能使用；只在 VM
  allocation context 传入 emergency=TRUE 且普通路径 bad_alloc 时启用。没有全局变量或
  TLS owner 推断。池按 8 B 对齐分割、释放合并；GC 归还退役异常/栈数组的空间，仍存活
  的静态根数组不可因退出 emergency 而被释放。额外统计 uses/live/peak/reserved。
- 强制 provider 普通提交先耗尽的双后端测试中，Java catch OOME 成功，首次应急峰值
  **48 B**、使用 **6 次**。GC 后 8 B 可回收，40 B 为初始化后存活数组；第二轮 catch/GC
  后 live 仍为 40 B，没有累计泄漏。256 KiB 取 VM 64 KiB 应急逻辑预算的四倍，既覆盖
  实测单例，也保留更深栈/不同初始化路径的余量，不以单例 48 B 当作通用上限。
- 池耗尽或应急元数据分配失败抛 `JavaPayloadEmergencyExhausted`，明确报告 backing
  应急资源不足；不转成 bad_alloc/heap_budget_exhausted 再构造 OOME。正常 provider
  失败的 JNI/Java OOME 转换保持不变。夹具仍可显式覆写普通提交限额验证此路径。
- 分级参数保持 16 KiB slab、8 KiB 阈值、64 级、64 个空 slab 缓存。committed 含预留池，
  slab_free 不含预留池；分析实景对比时同时列总 committed 和扣除应急池的普通 committed。

### 实现与 Release 决定

- 数组 Elements（八类）/PrimitiveCritical 从 store 取得 payload 的强类型 guest 地址，
  isCopy=FALSE。数组的 4 MiB staging arena、快照、写回及 token/kind/pointer lease 表删除；
  Region 的受检搬运仍保留，String 三种 lease/arena 与 NIO 不变。host-copy 无地址时明确失败，
  两组 guest binding 夹具与 GC 夹具改用 guest provider，无生产复制回退。
- pin 计数选在 store：这里已经拥有数组身份、Delete 检查与 GC roots 枚举，provider
  无需理解 VM 对象。长期 typed view 保活不可移动 backing；每次获取同址加一，非零 pin
  在 mark/weak 前为强根，无普通引用/长持有也不回收。Acquire/Release 通过显式 allocation
  context 先取得 VM 执行锁，再进 store 锁，和 GC 串行；跨线程不绑定获取者，detach 不释放。
- 按 Dalvik Jni.cpp:2383/2615，COMMIT 完全无操作，其余 mode（0、ABORT 及非法值）
  解除一次 pin，不复制/回滚，不校验 elems，也不区分 Elements/Critical；有效引用、类型、
  Region 边界及 VM/提交预算仍严格校验。实施决定追加于 ADR-0152，并引用 ADR-0153。
- pin=0 时再次 Release 不改变状态，只发布结构化 warn 与 warning ledger，包含数组身份、
  真实调用槽、guest LR；首次 pin>10（Dalvik kPinComplainThreshold）每数组警告一次。
  Stop 采样 store 的 pin_count/pinned_arrays/pinned_bytes；它们是 JNI 计数，不把 provider
  独立底层 borrow 统计冒充 JNI pin。全部 guest 线程和 CPU 停止并 join 后统一退役 store
  pin，残留时单条诊断记录数组数、字节数。可见性沿用现有 guest happens-before，不新增 fence。

  primitive 共用 process-owned guest provider；独立/headless 夹具显式选择 host-copy，
  guest JNI/GC 夹具使用 guest provider，直接借用无复制回退。
- 公共 char[]、StringBuilder/StringBuffer 和 substring 保留独立 block 的快照；不新增影子
  String.value/offset/count，不提供 const JNI 指针写入的支持或保护，也不用写 String 做别名验收。
- 将阶段 2 显式 allocation context 提升为共享 JavaPayloadAllocationContext，VM Reserve
  仍是唯一账本。String 创建默认收 32 B 对象头 + payload，已存在实例的 BindString 仅收
  payload；导入只补未收费项。Delete 退还 store 费用，sweep 只扣实例剩余费用，不双收/双退。
  分配失败完整回滚收费、target/emergency 与 block，NewString/UTF 的堆失败发布 Java OOME。
- Chars/Critical 直接返回同一 guest block 地址、FALSE，空串地址有效；按 String 身份
  计数 pin，两类 Release 都忽略 pointer/kind。无配对仅结构化 warn + ledger（String、槽、
  guest LR），首次 pin>10 告警一次；跨线程、detach 不清除。String 本体及 block 是 GC
  强根，比 Dalvik 只 pin char[] 更保守。停止/join guest 线程和 CPU 后统一退役并诊断。
- MUTF-8 仍编码复制、TRUE，既有 pointer/token 规则、NULL 兼容与 16 MiB 页对齐复制预算
  保持不变；其 lease 与 UTF-16 pin 独立。UTF-16 不再占 arena/复制预算，NewString 的输入
  范围与长度预检保留。Release 宽松语义与原 ADR 不同，已追加阶段 4 实施决定。
- String 采样为 kind=8，沿用七个长度桶，单列 live/peak/fail/pin；共享 provider 的
  committed/slab_free/size class/应急使用不重复分摊。保持 allocator 参数不变，先观测。
