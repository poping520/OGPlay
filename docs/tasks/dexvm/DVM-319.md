## 静态证据与结论

指定 dead_trigger C 日志只有注册、GLThread start、outside projection(epoch=0)三行；
tml 同为 NativeActivity，却有 View holder created/changed。重要限制：Logger 的 info
默认按 **category + message** first_and_count，epoch 是字段，不属于限流键。因此旧日志
**不能证明**后续未调用 SynchronizeContentView，亦不能证明之后 epoch 始终为0。
本单保留旧诊断，新增每窗口/原因的首条记录和可查询计数，不能用日志缺失冒充挂载失败。

只读 vd-119 producer 摘录与 vd-118 onCreate：先构造 Unity 容器，再执行父 onCreate，
随后 takeSurface(null)、初始化独立 GLSurfaceView/setRenderer/queueEvent，pc83 才将
getView 返回的容器交给 setContentView；初始化还经 Activity.runOnUiThread 投递。
真实 nativeInit 内部何时 addView、owner 上何时消费，静态摘录无法证明。
tml 的正常 View holder 是挂载控制，不能由相同 NativeActivity 父类推出相同容器/线程时序。

最可能的未决路径是“初始化投递后容器中尚无 producer”或“回调取消当前遍历身份”，
不是 takeSurface(null) 删除 Window 根。确定的产品缺陷是：首个 owner 投影屏障可在
SynchronizeContentView 之前泵送 Surface，选择仍是上次未挂载结果；内容同步原本也在
自身遍历之前选择。已修为在 owner 屏障及内容遍历完成后、Surface 交付前重新选择。
这能证明选择时序修正，**不证明真实游戏无投影首错已修复**。
