# DVM-359 · Bitmap 元数据查询

状态：实现、定向回归、逐项 handler 故障注入、BootDex 与 GTASA reached-fault 均已验证。未提交。
依赖：[DVM-244](DVM-244.md)、[DVM-358](DVM-358.md)。证据 `.local/dvm359/`。

## 根因与修改

Bitmap 不属于 BootDex 配方的类集合，而是 android_graphics.cpp 手写 intrinsic；缺少
getByteCount 导致 GTASA TextureAtlasCache.sizeOf pc0 在已解码图集上抛 UnsatisfiedLinkError。
后续 andImageView 初始化失败是 pending 异常的连锁错误。

新增四个 API19 public final 方法：getRowBytes()I、getByteCount()I、
getAllocationByteCount()I、isRecycled()Z。复用 BitmapState 的 width/height/config/recycled，
不新增状态。仅元数据查询允许读取 recycled 状态；未登记 receiver 仍抛原 IllegalStateException，
像素访问的回收检查不变。未知 config 按 dexvm.bitmap_decode 记账并抛 UOE。

[KitKat SkBitmap::ComputeRowBytes](https://android.googlesource.com/platform/external/skia/+/android-4.4_r1/src/core/SkBitmap.cpp)
对公开四种格式的行字节数为：ALPHA_8=width、RGB_565/ARGB_4444=width×2、
ARGB_8888=width×4，不做 4 字节对齐。源码取证 `.local/dvm359/SkBitmap.cpp`。
Java getByteCount 按 API19 Bitmap.java 的 getRowBytes()×getHeight()；无符号乘法配合
bit_cast 保留 Java 32 位 int 回绕，不饱和或额外截断。

API19 getAllocationByteCount 在 mBuffer 非空时返回内容缓冲区长度，mBuffer 为空的
native backing 不可重配置，返回 getByteCount。本项目拒绝 inBitmap，且未提供复用/重配置，
所以 allocation 始终等于内容大小。recycle 保留尺寸/config，前三项仍返回原结果。

## 已知差异

NDK AndroidBitmap 的 BitmapPixels::Stride() 仍做 4 字节对齐，Java getRowBytes 不对齐；
奇数宽 RGB_565/ARGB_4444/ALPHA_8 两者不一致。本单记录、不修改 NDK backing 或 stride。
位图像素仍不计入 VM 堆/growth limit，不能将本查询值视为 VM 已实现像素堆记账。

## 后续依赖（GTASA 路径）

- PackedImage.draw → Canvas.drawBitmap(Bitmap,Rect,RectF,Paint)。
- PackedImage 分块 → Bitmap.createBitmap(Bitmap,IIII)。
- TextureAtlas flags≠0 且 scale≤0.5 → inSampleSize 2/4 被 BitmapFactory 拒绝。
- 位图像素不计入 VM 堆/growth limit（API19 计入 Java 堆）。

本单不实现 getConfig/hasAlpha/setHasAlpha/copy、其他 createBitmap 或 Canvas.drawBitmap
重载、BitmapFactory 采样；上述依赖只记录，不修复。
