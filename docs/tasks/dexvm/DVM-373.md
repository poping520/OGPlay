# DVM-373 · VideoView 跨 guest 线程释放

状态：修复及 macOS Release 菜单音频验证完成；未做正式 title gate 或跨平台验收。日期：2026-11-05。

## 目标与依赖

修复非 UI guest 线程释放 VideoView 后音轨继续混音的问题，保留 UI metadata 的 owner 规则。
依赖 DVM-303 的代际 metadata/JavaTraversal、DVM-189 的唯一音频混合路径；不新增外部依赖。

## 原因与实现

Tales 原 APK 经 `build/release/ogplay-cli library run com.amazon.games.Tales --mode diagnostic`
进入 2560×1600 菜单。游戏渲染线程通过 JNI 调用 `fVideoView.stop()`，Java 的
`stopPlayback → VideoMediaPlayer.release → nativeRelease` 被误用的 `RequireVideoOwner`
拒绝。Java 已撤掉 player 身份并推进 generation，native decoder 却仍保存 playing 状态；
游戏吞掉异常后继续，两个已撤下画面的开场视频音轨继续叠加菜单音乐。

- 本地 AOSP `framework/base/core/java/android/widget/VideoView.java::stopPlayback` 直接
  stop/release MediaPlayer；释放音轨不应依赖 UI metadata 的 owner 检查。
- nativeRelease 仍核验 generation，任意 guest 执行线程均可在视频锁内移除源，立即停止
  后续 PCM 混音；decoder 移出锁后销毁，避免持音频共享锁 join。
- owner 调用同步清理 intrinsic/requestLayout；其他 guest 线程只登记待撤销的 View 引用。
  主线程视频泵在遍历播放源前清理 metadata，待办由 session GC root 保活；`PumpVideo` 不再
  因源表为空提前返回，否则释放最后一个视频后待办无人处理。若 View 已成功重开 decoder 则
  跳过旧清理，重开失败（无 decoder）仍撤销旧尺寸；sweep/teardown 清除待办。
- 打开源、测量和 prepared metadata 交付仍只接受 UI owner。未改 OpenSL、SDL 水位、
  解码算法或增益；生产代码无游戏分支，临时 PCM 探针已移除。
